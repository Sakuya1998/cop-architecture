# COP 架构原则

## Purpose

定义所有后续设计必须遵守的长期原则和决策优先级。

## Scope

- 领域边界
- 松耦合
- API-first
- 可观测
- 安全
- 可演进

## Non-goals

- 具体产品选型
- 服务清单
- 部署参数

## Context

本文承接 `COP-VIS-001` 与 `COP-VIS-002` 确立的平台方向和范围，为后续架构与领域设计提供共同决策规则。详细逻辑架构和领域边界仍分别由 `COP-ARCH-002`、`COP-DOM-001` 定义。本文保持 `draft`；在状态变为 `accepted` 前，不形成 `cop-platform` 的实现约束。

## Architecture or Model

### Decision Priority

当原则之间发生冲突时，按以下顺序裁决：

1. 安全、权限与隔离边界。
2. 数据正确性与稳定资源身份。
3. 可靠性与可运维性。
4. 可演进性与开放集成。
5. 简单性与交付效率。

高优先级原则覆盖低优先级原则。同级原则冲突时，选择更简单、可验证、可回退的方案。无法明确裁决或需要改变优先级时，必须进入 RFC/ADR 流程，并评审相关权威文档。

### Core Principles

#### Secure by Default

- 默认拒绝访问，并按最小权限授予能力。
- 组织、租户、身份、资源和访问上下文必须显式表达。
- 只保存受控凭据引用，不得把敏感值作为普通领域数据传播。
- 敏感操作的主体、目标、结果和时间必须可审计。
- 管理面、受管环境和外部系统不能仅因网络位置而默认互信。

#### Stable Resource Identity and Data Correctness

- 统一资源身份必须稳定、可追踪，并具有明确的权威来源。
- 权威来源约束身份语义与写入责任，但不预设单一服务或数据库。
- 外部数据必须暴露来源、同步状态和新鲜度。
- 冲突、未知和过期状态必须显式表达，不能静默覆盖为成功。

#### Domain-oriented Boundaries

- 按业务能力、数据所有权和变化原因划分领域。
- 每个边界必须有明确的职责、输入、输出和依赖。
- 领域边界不等同于微服务、代码包或数据库数量。
- 技术分层与流程可以组织领域内部，但不能替代领域责任边界。

#### Domain Data Ownership

- 领域拥有自己的写模型、不变量和写入语义。
- 禁止跨领域绕过 Contract 直接写入其他领域的数据存储。
- 跨领域读取必须经过稳定 Contract 或受控读模型。
- 复制的读模型不能成为未声明的新权威来源。

#### Contract-first Interaction

- Contract-first 是对 `Scope` 中 API-first 的扩展而非否定；API 是跨边界 Contract 的一种形式。
- 先定义语义、所有权、兼容性和失败行为，再选择通信技术。
- 需要即时结果的查询或命令可以使用同步 API；状态传播与解耦可以使用事件。
- 不强制所有交互采用同步方式或全部事件化。
- Contract 可以版本化演进，并必须定义拒绝、超时、重试、部分失败和延迟传播语义。

#### Observable and Recoverable Operations

- 可运行组件必须暴露健康、依赖、处理状态和数据新鲜度信号。
- 隔离故障，避免单一外部依赖的影响无边界扩散。
- 重试必须幂等，或具备等价的重复处理保护。
- 降级、恢复和重新同步路径必须明确且可验证。
- 事件消费者必须处理重复、乱序和延迟，不能把未声明的到达顺序作为不变量。

#### Open and Evolvable Architecture

- 云厂商、Kubernetes 和可观测产品的语义必须通过 Adapter 或等价稳定边界隔离。
- 核心领域模型不能绑定单一云厂商、集群或存储引擎。
- Contract 变更必须有兼容策略；重大变更必须有迁移和回退路径。
- 自托管必须能够独立运行，且不能破坏未来组织或租户隔离能力。

#### Simplicity and Incremental Evolution

- 只引入当前已评审需求证明需要的复杂度。
- 选择最小、可理解、可验证、可替换、可回退的设计。
- 不为路线图之外或未经过 RFC/ADR 的能力预建架构。
- 不得以交付效率降低安全、数据正确性或恢复能力。

### Review and Evidence

- 新增或改变领域边界、数据权威、跨领域 Contract、安全或租户边界、故障行为、外部集成边界、迁移路径的设计，均视为重大设计。
- 每项重大设计必须说明适用原则和优先级、领域/数据/Contract 所有权、安全/隔离/故障/兼容性影响、验证证据，以及迁移/回退/替代方案。
- 可自动化的 Contract 兼容、权限边界、幂等、数据不变量、迁移和回退检查必须进入测试或 CI。
- 领域边界、责任归属、复杂度、供应商绑定和运营风险必须进入架构评审清单。
- 同步交互必须定义拒绝、超时、重试和部分失败；异步交互必须定义重复、乱序、延迟和消费失败；外部同步必须定义来源、同步状态、新鲜度和冲突状态。
- 未知、降级和失败必须与成功明确区分。

### Exception Governance

- 违反高优先级原则默认阻断。
- 例外必须有 RFC/ADR，记录原因、范围、备选方案、责任人、验证措施，以及到期或退出条件。
- `accepted` ADR 只能批准明确、有边界的例外，不能隐式改变原则文档。
- 长期改变原则或优先级时，必须更新 `COP-PRI-001` 和受影响的权威文档。
- “临时方案”不能绕过评审。

### Success Criteria

- 重大设计能够指出适用原则、优先级和验证证据。
- 安全、权限、租户和凭据边界显式。
- 稳定资源身份、来源、同步状态和新鲜度可追踪。
- 领域写模型和不变量具有唯一责任方，不跨领域直接写入存储。
- 跨领域交互定义 Contract、失败语义和兼容策略。
- 故障隔离、幂等重试、降级和恢复可验证。
- 外部依赖通过稳定边界接入，核心模型不绑定单一供应商。
- 重大变更可迁移、可回退；例外具有获批 RFC/ADR。

## Constraints

- 不得绕过 RFC/ADR 流程引入重大架构决策。
- 不得与相关 `accepted` 权威文档产生冲突。
- 交付速度不得成为绕过高优先级原则的理由。
- 领域不得直接写入其他领域的数据存储。
- 外部产品语义不得泄漏到核心领域模型。

## Quality Attributes

后续评审必须覆盖安全性、正确性、可靠性、可运维性、兼容性和可演进性，并以可验证证据说明设计如何满足这些质量属性。
