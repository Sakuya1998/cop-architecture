# COP 系统上下文内容设计

## 1. 目标

将 `COP-ARCH-001` 从初始化骨架补充为可评审的系统上下文文档，明确 COP、用户、受管环境、业务工作负载和外部平台之间的系统级关系、责任归属、权威数据边界、信任边界与失败边界。本文只定义系统上下文，不替代逻辑架构、领域模型、安全架构、基础设施设计或具体集成 Contract。

## 2. 系统边界

- COP 系统边界包含中央管理面，以及部署在受管环境中的最小采集、连接和状态上报组件。
- 平台工程、SRE 与运维、安全、审计与管理人员位于 COP 系统边界之外，通过 COP 使用平台能力。
- 云厂商、Kubernetes、外部身份提供方、Telemetry 平台、通知系统、对象存储和业务工作负载均位于 COP 系统边界之外。
- 云资源、Kubernetes 对象和业务工作负载的实际执行、最终状态及产品语义始终由外部平台负责。
- COP 是资源与运营上下文的集成和协调层，不替代外部平台的执行、身份认证、Telemetry 存储、渠道投递或对象持久化能力。

## 3. 用户角色

系统上下文采用三组用户角色，既保留职责差异，又避免把组织岗位直接映射成内部组件：

- **平台工程：** 配置云账号和 Kubernetes 集群接入，维护资源目录、组织和租户边界。
- **SRE 与运维：** 查询资源、状态、Telemetry、Dashboard 和 Alert，执行日常巡检、异常定位和变更后核查。
- **安全、审计与管理协作用户：** 管理访问策略，查询审计记录、访问上下文和运营态势。

## 4. 外部系统与关键交互

### 4.1 云厂商 API

COP 使用最小权限凭据读取资源元数据和状态，执行发现与持续同步。COP 不通过本文定义云资源创建、变更、删除或最终状态控制能力。

### 4.2 Kubernetes API

COP 读取集群对象、关系和状态，建立统一资源上下文。COP 不控制业务工作负载的构建、发布、调度或运行时生命周期。

### 4.3 外部身份提供方

外部身份提供方负责用户认证、身份生命周期和身份声明。COP 验证声明，并负责组织与租户成员关系、角色映射、最终授权决策和审计。

### 4.4 Telemetry 平台

Telemetry Collectors、指标、日志与追踪存储以及查询引擎保持外部。COP 接收或查询运营信号，维护接入配置、资源关联、查询上下文、同步状态和必要的派生状态，不成为原始 Telemetry 数据的权威存储。

### 4.5 通知系统

COP 负责用户可见的告警定义、资源关联、通知策略、接收目标引用、投递请求和审计。外部通知系统负责渠道适配、最终投递和渠道侧结果。

### 4.6 对象存储

对象存储是可选的外部基础设施依赖，用于备份、导入导出和大对象归档。COP 管理对象用途、引用、保留意图和业务生命周期，不把对象存储作为核心事务数据或原始 Telemetry 的权威存储。

### 4.7 业务工作负载

业务工作负载只通过云、Kubernetes 与 Telemetry 关系进入 COP 运营上下文。业务应用的构建、发布、托管和运行时生命周期保持在 COP 系统边界之外。

## 5. 权威责任与数据归属

| 领域 | COP 负责 | 外部系统保留的权威职责 |
| --- | --- | --- |
| 资源 | 稳定身份、统一模型、目录、关系和同步状态 | 云与 Kubernetes 资源的实际状态、执行和厂商语义 |
| 身份与访问 | 组织/租户成员关系、角色映射、授权决策和审计 | 用户认证、身份生命周期和身份声明 |
| Telemetry | 接入配置、资源关联、查询上下文和必要的派生状态 | 原始指标、日志、追踪数据及查询引擎内部实现 |
| Alert | 用户可见的告警定义、资源关联、状态和通知策略 | 外部 Telemetry 引擎的数据计算与执行语义 |
| 通知 | 投递请求、目标引用、策略上下文和审计 | 渠道适配、最终投递和渠道侧结果 |
| 对象存储 | 对象用途、引用、保留意图和业务生命周期 | 对象持久化、可用性和存储实现 |
| 业务工作负载 | 资源与运营信号上下文 | 构建、发布、托管和运行时生命周期 |

凭据只通过受控引用和明确的信任边界使用。具体 Secret 或 KMS 产品由后续安全与基础设施文档定义。

## 6. 上下文图设计

目标文档使用 Mermaid `flowchart` 表达系统上下文：

- 一个 COP 系统框表示中央管理面和最小受管环境组件，不展开 Portal、API、服务、数据库或其他内部组件。
- 三组用户角色位于系统框一侧，六类外部平台位于另一侧，业务工作负载位于受管环境语义下但保持在 COP 系统边界之外。
- 每条关系标明交互目标和主要数据方向，不使用无语义的通用“调用”标签。
- 图中明确 COP 对云和 Kubernetes 的交互是发现、读取和同步，对 Telemetry 的交互是接收或查询，对通知系统的交互是请求投递，对对象存储的交互是可选备份、导入导出和归档。
- 图后使用责任表和交互说明补充无法在图中完整表达的权威数据、失败和信任语义。

## 7. 信任、网络与失败边界

- 受管环境组件主动建立到中央管理面的加密出站连接，默认不要求从管理面入站访问受管环境。
- COP 访问外部平台时使用独立身份、最小权限和可审计的凭据引用。
- 所有用户请求和外部交互携带明确的组织、租户与资源归属上下文；授权默认拒绝。
- 外部身份声明只有在完成验证、租户映射和角色映射后才能参与 COP 授权。
- 每个外部连接暴露来源、最近成功时间、新鲜度、错误状态和重试状态，不把陈旧数据呈现为实时事实。
- 同步、上报和投递重试具备幂等语义或等价的重复处理保护。
- 单个账号、集群或外部平台故障不得破坏其他连接或统一资源目录，未知、陈旧、降级和失败状态必须与成功状态可区分。
- 外部平台语义通过 Adapter 或等价稳定边界隔离，不得泄漏到统一资源身份和核心领域模型。
- 关键接入、授权、配置变更、同步和通知行为可观测、可追踪、可审计。
- `COP-ARCH-001` 只定义系统级约束和可观察结果，不定义协议、端口、超时、重试次数或数值化 SLO。

## 9. 明确不做

- 不拆分 COP 内部组件、服务或部署单元。
- 不定义服务 API、事件字段、数据库表、消息协议或网络端口。
- 不选择云厂商、身份、Telemetry、通知、对象存储、Secret 或 KMS 产品。
- 不定义外部系统内部实现、容量管理、查询执行或渠道投递机制。
- 不增加资源创建、变更、删除、自动修复、Workflow、Automation 或 AI 能力。
- 不修改 `COP-ARCH-002`、`COP-DOM-001` 或其他权威文档。
- 不把 `COP-ARCH-001` 标记为 `accepted`。

## 10. 成功标准

- 读者能从上下文图快速识别 COP 系统边界、三组用户角色、六类外部系统和业务工作负载。
- 每项交互都能判断发起方、数据方向、COP 职责和外部权威职责。
- 统一资源身份和运营上下文属于 COP，资源实际执行与最终状态属于外部平台。
- 身份认证与 COP 授权、原始 Telemetry 与资源关联、通知请求与最终投递之间的责任边界明确。
- 对象存储明确为可选依赖，不成为核心事务数据或原始 Telemetry 的权威存储。
- 管理面与受管环境之间采用由受管组件发起的加密出站连接，且身份、凭据、网络和数据传输边界明确。
- 外部连接的数据来源、新鲜度、错误和重试状态可观察；同步、上报与投递重试具备幂等语义并隔离故障。
- 文档与 `COP-VIS-001`、`COP-VIS-002` 和 `COP-PRI-001` 一致，不引入内部实现或供应商选择。
