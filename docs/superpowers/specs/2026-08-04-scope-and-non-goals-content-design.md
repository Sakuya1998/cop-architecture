# COP 范围与非目标内容设计

## 1. 目标

将 `COP-VIS-002` 从初始化骨架补充为可评审的范围文档，明确 COP 的平台职责、外部系统边界、部署形态、首版范围、明确非目标和新需求判定规则。本文定义职责边界，不替代 MVP、系统上下文、逻辑架构或控制面/数据面文档。

## 2. 已确认的职责边界

### 2.1 COP 负责

- 维护统一资源模型、稳定资源身份、资源目录和资源关系。
- 管理云账号与集群的接入配置、凭据引用、发现和同步任务。
- 维护 Metadata/CMDB 语义及资源来源、状态和生命周期信息。
- 将资源与指标、日志、告警、权限和审计上下文关联。
- 提供统一查询、运营视图、Dashboard、Alert、IAM 和 Audit 能力。
- 定义平台自身的组织、租户和访问边界。

### 2.2 COP 集成但不替代

- 云厂商 API 和 Kubernetes API。
- 外部身份提供方。
- Telemetry Collector、指标、日志和追踪存储。
- 通知、对象存储及其他基础设施系统。

COP 可以部署或连接这些组件，但不在范围文档中承担其内部实现职责。

### 2.3 外部系统负责

- 云资源和 Kubernetes 工作负载的实际执行与最终状态。
- 业务应用的构建、发布和托管。
- 云厂商产品语义和底层基础设施实现。
- 可观测存储引擎内部的数据组织、查询执行和容量管理。

## 3. 部署与环境边界

### 3.1 当前交付边界

- COP 以自托管为首要交付形态，管理面由使用组织自行部署和运营。
- 一个 COP 管理面可以连接多个云账号、多个 Kubernetes 集群和多个受管环境。
- 受管环境只部署完成采集、连接和状态上报所需的最小组件。
- 管理面、受管环境和外部系统之间必须存在明确的身份、凭据、网络和数据传输边界。
- COP 不要求业务工作负载迁入 COP 所在集群。

### 3.2 SaaS-ready 边界

- 组织、租户、成员关系、资源归属和访问上下文从设计初期保持明确。
- 数据模型和接口不得依赖全局只有一个组织或租户的假设。
- 自托管部署可以使用单组织模式，但不能破坏未来租户隔离能力。
- 当前阶段不交付 SaaS 计费、订阅、运营后台、客户生命周期管理或正式服务等级承诺。

## 4. 阶段范围

### 4.1 首版范围

- 云账号和 Kubernetes 集群接入。
- 资源发现、采集和持续同步。
- Metadata/CMDB 及统一资源目录。
- 指标、日志和基础可观测信号关联。
- Dashboard 和告警。
- IAM、访问控制和审计。

这些项目只定义范围，不替代 `COP-ROAD-002` 对 MVP 完成条件的详细定义。

### 4.2 首版明确不做

- 业务应用托管。
- 单一云厂商专用平台。
- 资源创建、变更、删除和自动修复。
- Workflow、Automation、FinOps 和插件市场。
- AI/RAG 的详细能力。
- SaaS 计费、订阅和正式运营能力。
- 具体 API、服务拆分、部署参数和技术选型。

未来自动化和 AI 能力必须经过路线图、RFC/ADR 和对应权威文档评审后再进入实现范围。

## 5. 范围判定规则

新需求进入 COP 范围前必须回答：

1. 是否直接服务平台工程、SRE 或运维团队？
2. 是否增强统一资源模型、运营上下文、治理或运营闭环？
3. 属于 COP 自有职责，还是仅需与外部系统集成？
4. 是否要求 COP 替代云厂商、业务平台或存储引擎的职责？
5. 属于当前 MVP、后续路线图阶段，还是尚未评审的能力？
6. 是否影响组织、租户、凭据、网络或数据隔离边界？

无法明确归属、跨越既有边界或引入重大职责变化的需求，必须先经过 RFC/ADR 和相关权威文档评审。

## 6. 边界设计成功标准

- 每项能力都能明确归入 COP 负责、COP 集成、外部负责或当前不做。
- 自托管部署不依赖 COP 官方 SaaS 服务即可独立运行。
- 多云账号和多集群接入不改变 COP 的核心资源模型。
- 业务工作负载无需迁入 COP 管理面。
- 当前 MVP 不依赖资源变更、Workflow、Automation 或 AI 才能形成完整闭环。
- 未来 SaaS 演进不要求推翻组织、租户和资源归属模型。

## 7. 目标文档结构

只修改 `docs/vision/scope-and-non-goals.md` 的正文，不修改 YAML 元数据、ID、状态、版本、related、RFC 或 ADR 字段。保留现有 H1、`Purpose`、`Scope`、`Non-goals` 和 `References`：

- `Context`：说明本文承接已批准的平台愿景，并限定与 MVP、架构和领域文档的关系。
- `Architecture or Model`：使用 `Responsibility Boundary`、`Deployment Boundary`、`Stage Boundary`、`Scope Decision Rules`、`Success Criteria` 子节呈现已确认内容。
- `Constraints`：保留 RFC/ADR 和 accepted 文档约束，增加自托管独立运行、外部执行权和 SaaS-ready 边界。
- `Quality Attributes`：强调边界清晰、租户隔离、安全连接、可演进和兼容性，不写技术参数。
- `Implementation Guidance`：保留 draft 门禁，未 accepted 前不得据此生成生产实现。

## 8. 明确不做的事情

- 不修改 `COP-VIS-001`、`COP-ROAD-002` 或 `COP-ARCH-001`。
- 不改变首版 MVP 的详细完成条件。
- 不定义服务拆分、API、数据库、部署参数或具体供应商产品。
- 不把 `COP-VIS-002` 标记为 `accepted`。
- 不创建实现代码或改变 `cop-platform` 仓库。

## 9. 验收条件

1. `COP-VIS-002` 的 YAML 元数据完全不变，状态仍为 `draft`。
2. 文档明确区分 COP 负责、COP 集成和外部系统负责。
3. 文档明确自托管优先、多账号多集群、最小受管组件和 SaaS-ready 边界。
4. 文档明确首版为接入、发现、采集、关联、展示、告警、IAM 和审计，不执行资源变更或自动修复。
5. 文档包含完整的范围判定规则和边界设计成功标准。
6. 文档不复制 `COP-ROAD-002` 的完成条件，也不引入技术实现或商业承诺。
7. 三个既有相对链接均解析，未出现 `TBD`、`TODO` 或 `lorem ipsum`。
8. `git diff --check` 通过，实施改动仅限规格、计划和目标范围文档。
